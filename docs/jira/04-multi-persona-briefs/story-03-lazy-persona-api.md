## User story
As a sales rep, I want the persona I chose to be ready as fast as possible and the other personas to generate only if I actually open them, so that I'm not waiting on — or spending free-tier LLM calls on — briefs I never look at.

## Description
This story wires persona through the API and the background generation lifecycle so that each persona's brief has an independent status and can be fetched, generated, and regenerated on its own. Every brief-related endpoint takes an optional `persona` query parameter; when it is omitted, the endpoint falls back to the meeting's primary persona. This keeps existing single-persona flows working unchanged while making the persona dimension explicit everywhere it matters.

Generation is lazy by design. When a meeting is created, three Brief rows are seeded — the primary persona in `generating` and the other two in `pending` — and only the primary persona's background task is scheduled immediately. The other personas stay dormant until someone actually views them. On `GET /meetings/{id}/brief?persona=`, if the requested persona's row is missing or still `pending`, the endpoint flips it to `generating`, schedules its background task, and returns a `generating` status so repeated polls don't re-schedule duplicate work. Once ready, the same endpoint returns the parsed `BriefContent` plus the rendered HTML for that persona; on failure it returns the error. This holds free-tier usage to roughly one LLM call per meeting unless the rep toggles personas.

Each persona's brief is generated by a background task that opens its own database session and is exception-safe: any failure is caught and written as `status=error` rather than crashing the server. The task also mirrors status onto the parent meeting, but only when the persona being generated is the meeting's primary persona — so the dashboard's headline status reflects the primary brief while secondary personas track their own status independently. Persona-scoped regeneration resets just that persona's row (status back to `pending`, content/html/error cleared) and re-schedules its task, again mirroring to the meeting only for the primary persona.

## Acceptance criteria
```gherkin
Scenario: Only the primary persona generates on meeting create
  Given a meeting is created with "sdr" as its primary persona
  When the meeting is saved
  Then three brief rows exist: the SDR row generating, and the AE and SE rows pending
  And only the SDR background generation task is scheduled
```
```gherkin
Scenario: A secondary persona generates lazily on first view
  Given a meeting whose SE brief row is still pending
  When GET /meetings/{id}/brief?persona=se is called
  Then the SE row is flipped to generating and its background task is scheduled
  And the response status is "generating"
  And subsequent polls return "generating" without scheduling the task again
```
```gherkin
Scenario: Persona-scoped fetch and regenerate are isolated
  Given a ready AE brief and a ready SE brief for the same meeting
  When regenerate is called with persona=se
  Then only the SE row is reset to pending and re-scheduled
  And the AE brief and the meeting's primary status are left untouched
```
```gherkin
Scenario: A persona brief that fails generation is reported, not crashed (edge case)
  Given generation raises an error for one persona
  When its background task runs
  Then that persona's brief row is written with status "error" and the error message
  And the server keeps running and other personas are unaffected
```

## Technical notes (reference)
- Key files: `backend/app/api/briefs.py` (`GET /meetings/{id}/brief` with `persona=`, lazy flip to `generating`), `backend/app/api/meetings.py` (`create_meeting` seeding of AE/SDR/SE rows, `generate_one_task`/`_run_generation`, `regenerate_brief` with `persona=`).
- `p = persona or meeting.persona` resolution is applied consistently across fetch and regenerate; unresolved persona defaults to the meeting's primary.
- `_run_generation` opens its own `Session`, is catch-all exception-safe (`status=error`), and mirrors status onto `Meeting.brief_status` only when the persona is primary (`is_primary`).
- POC shortcut: FastAPI `BackgroundTasks` (not a job queue); lazy generation keeps free-tier requests to ~1 per meeting unless personas are toggled.

## Definition of Done
- [x] All brief endpoints accept an optional `persona` param falling back to the meeting's primary persona.
- [x] On create, all three persona rows are seeded and only the primary persona's task is scheduled.
- [x] `GET brief?persona=` lazily generates a missing/pending persona and returns `generating` without duplicate scheduling.
- [x] `regenerate?persona=` resets and re-schedules only the targeted persona's row.
- [x] Background generation is exception-safe and mirrors status to the meeting only for the primary persona.
